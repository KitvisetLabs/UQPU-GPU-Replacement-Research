## 4. Matched follow-up design for RG-EQN-008

The new paper motivates a width factor, not an assumption that wider search wins. Before any run:
- pin dataset source/version/license/acquisition bytes, data/split/preprocessing/grammar/unit/acceptance hashes, and group-disjoint law-family/scale manifests;
- hold the model/checkpoint, source revision, controller, runtime/dependencies and all rules fixed; make width the only preregistered configuration change;
- use width arms such as 1/2/4/8/16 only if declared before registration and feasible under the pinned resource envelope;
- use at least 30 shared seeds per arm and equal hard ceilings for wall clock, CPU-core seconds, peak memory, accelerator time, candidate evaluations, generated tokens and total cost;
- report accepted-candidate rate and held-out error with uncertainty, constraint violations, counterexamples, false discoveries, failed searches/retries, resource usage and measured cost per accepted candidate;
- reserve entire law families and scales for blind tests and require the same independent physical/math acceptance gate for every arm.

**Falsifier:** no robust advantage if the width effect disappears under held-out family/scale tests, is explained by resource mismatch/leakage, increases false discoveries, or improves wall-clock alone without improving accepted useful output per total resource/cost. Hashes bind declared artifacts but do not authenticate their bytes; source artifacts and lockfiles must remain retrievable and independently verified.
