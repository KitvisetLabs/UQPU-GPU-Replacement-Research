## 3. Local classical scale screen

The three deterministic `seeded_erdos_renyi_maxcut(n, 0.5, seed)` fixtures were measured in separate Python processes so each `ru_maxrss` value begins with a fresh process. The environment reports Python 3.12.14, Linux 6.18.44 x86_64, and nine logical CPUs.

| Nodes / seed | Edges | Exact states | Exact objective | Exact elapsed | Greedy objective / gap | Process `ru_maxrss` |
|---|---:|---:|---:|---:|---:|---:|
| 6 / 42 | 9 | 64 | -7 | 0.000172593 s | -7 / 0 | 16,640 KiB |
| 10 / 43 | 20 | 1,024 | -15 | 0.004081244 s | -15 / 0 | 16,640 KiB |
| 14 / 44 | 49 | 16,384 | -36 | 0.146436963 s | -36 / 0 | 16,640 KiB |

Exact enumeration has both a 1,048,576-state cap and a 30-second wall-clock deadline. It permits an optimum claim only after complete state-space traversal; a unit test proves that an early state-cap stop disables that claim. The greedy equality on these three small generated fixtures is not evidence of general heuristic quality, competitive solver performance, quantum disadvantage, or scaling behavior. A naive objective ratio is intentionally null because the negative QUBO objectives make such ratios misleading.

The Python `resource` documentation identifies `ru_maxrss` as maximum resident set size and warns that resource units can be platform-dependent. This cycle therefore records Linux KiB semantics and does not subtract a baseline or infer incremental memory.
